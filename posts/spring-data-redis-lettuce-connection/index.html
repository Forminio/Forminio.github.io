一段突然变慢的缓存查询
#

一种典型现象：压测时 Redis 延迟从 1ms 蹿到几十甚至上百 ms，P99 直接拉胯。参数改了不少却没效果，最后发现问题出在 Lettuce 的连接管理——不是 Redis 慢，是客户端自己把请求堵在门口了。这个坑值得讲透。

先说清楚：Spring Boot 默认是 Lettuce，而且默认没连接池
#

很多人以为 Spring Data Redis 自带连接池，其实默认用 RedisTemplate 的话，底层 Lettuce 是多路复用单连接（共享连接），并没有连接池。如果你用了共享连接模式，多个线程同时塞请求，遇到慢命令就会互相排队。

要用连接池，必须手动引入 commons-pool2 并配置：

<dependency>
  <groupId>org.apache.commons</groupId>
  <artifactId>commons-pool2</artifactId>
</dependency>
spring:
  data:
    redis:
      lettuce:
        pool:
          enabled: true
          max-active: 8
          max-idle: 8
          min-idle: 0
          max-wait: 3000ms

关键参数三个：max-active（最大并发连接）、max-idle（空闲保留）、max-wait（借不到连接时最多等多久）。max-wait 记得设短点，否则拿不到连接会一直干耗，接口层层叠加就雪崩。

一个典型坑：慢命令 + 共享连接 = 全体排队
#

一个典型坑：某个接口对 Redis 做了 KEYS 扫描，KEYS 是 O(N) 全库遍历，在共享连接模式下，这条命令一跑，这台连接上的所有其他请求都跟在后面排，延迟瞬间集体恶化。

所以经验第一条：读路径别做 KEYS、SMEMBERS 这种大集合操作，尤其是用了共享连接的时候。要么换连接池隔离快慢命令，要么干脆从命令本身下手。

断线重连和超时，也别忽略
#

Redis 重启、网络抖动时，Lettuce 建立连接会失败，默认超时时间可能很长，接口直接卡住。把超时配好，让失败快速暴露而不是默默挂起：

spring:
  data:
    redis:
      timeout: 2000ms

还有 shutdown-timeout，服务优雅停机时给 Lettuce 一点时间排空在途请求，避免停机瞬间请求被截断。

连接池多大才合适
#

max-active 不是越大越好。连接多了占用 FD，也挤占 Redis 端的连接数。可以按经验公式起步：活跃并发 × 平均耗时估算同时需要的连接数，再留 20%-30% 余量，压测时观察 max-active 是否触顶、max-wait 是否经常超时来微调。

判断连接是否吃紧，就看两个信号：max-wait 频繁触发（借不到连接）、监控里连接使用率长期接近 max-active。真到这种程度，先优化命令和数据结构，比无脑加连接更管用。

Lettuce 这层水很深，连接池怎么选、空闲连接怎么保活防止被服务端掐断、shareNativeConnection 的开关各有什么影响，这些细节单开一篇才能讲清楚。这部分的坑就先记到这儿，后面单独聊。
